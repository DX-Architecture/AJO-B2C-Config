1.1 Decisioning 
Decisioning in Journey Optimizer is a shared offer engine. You build items once in a catalog, then an email (or other channel) asks a decision policy 
for the best N items for that profile and renders their attributes in the message. (See structure 1.1) 
1.2 How a decision is made 
When a profile hits a journey or campaign that contains a decision policy, the engine does this for that person. (See structure 1.1) 
 
What each layer does: 
 
1.​
Catalog / items — the inventory of offers (name, dates, priority, custom fields, content). 
2.​ Collections — dynamic groups of items, based on catalog attributes (for example category = yoga). 
3.​ Eligibility — who can see an item.  
a.​ Audience = precomputed membership (can be stale).  
b.​ Decision rule = evaluated on every decision against current profile/context. 
4.​ Capping — how often an item can be shown (per profile or globally; by decision event, impression, click, or custom event). 
5.​ Ranking — which eligible item wins: item priority, a ranking formula, or an AI model. 
6.​ Decision policy — the runtime container: how many items to return, which selection strategies to run (in sequence), and fallback if nobody 
qualifies. 
1.3 Create decision items 
Decisioning → Catalogs → Create item 
1.​
Attributes: name, description, start/end dates, priority (integer; higher wins when ranking is “offer priority”), tags, custom attributes. 
Optional: Journey Optimizer or AEM content fragments. 
2.​ Eligibility: default is everyone. Restrict with: 
a.​ Audiences — profile already in the audience 
b.​ By rule — evaluated at decision time (use this when you need current profile or context, for example weather) 
3.​ Capping (optional, up to 10 rules): event type (decision / impression / click / custom), scope (offer-level vs placement), type (in total vs per 
profile), threshold, reset frequency. 
4.​ Save as Draft, then Approve. Only approved, in-date items can be delivered.

3.1 Is decisioning in AJO B2C similar to Adobe Recommendations? 
Both pick items from a catalog for a person. Adobe Recommendations (Target) is a behavioral product/content recommender. AJO Decisioning is a 
governed next-best-offer engine. 
 
The difference is rules vs affinity. 
 
●​ Decisioning: “Gold members can see this 10% offer, once per week, not if they already have the product.” 
●​ Recommendations: “People who viewed this shoe also viewed these.” 
 
Use Decisioning for which promo/message wins across journeys. Use Recommendations for which products to show from a large catalog. They can 
run together; they are not substitutes.

1.1 Overview 
Journey capping helps you limit the number of journeys a profile can be enrolled in, preventing communication overload. In Journey Optimizer, you 
can set two types of capping rules: 
 
●​ Entry capping limits the number of journey entries over a given period for a profile. 
●​ Concurrency capping limits how many journeys a profile can be enrolled in simultaneously. 
○​ See visual 1.1 
2.1 Journey capping 
Two rule types, both live under Business rules, on a rule set with domain Journey: 
 
●​ Entry capping — max journey entries over a period. Example: no more than 5 journeys in a month. Duration is UTC (daily resets at midnight 
UTC). Upcoming scheduled journeys that use the same rule are counted too, so a high-priority journey later in the month can block a 
lower-priority one now. 
●​ Concurrency capping — max journeys a profile can be in at the same time. Example: only 1 journey at once. 
○​ Concurrency also has Prioritization look ahead (1 / 7 / 30 days). It looks at upcoming scheduled Read audience journeys that share 
the rule set. If a higher-priority one is coming, the profile is held out of the lower-priority journey so the slot is free. 
○​ Apply it on the journey: Properties → Capping rules. Activate the rule and the rule set. If you publish immediately, suppression can 
take up to 10 minutes. 
3.1 Journey arbitration 
Arbitration runs only when a cap would be exceeded. Eligible journeys that share the rule set are ranked; the top ones fill the remaining slots; the rest 
are excluded. 
●​ Default: priority score (0–100) on the journey properties. Higher wins. 100 effectively guarantees entry. Same score = no reliable tie-break, 
so keep scores unique. 
●​ Optional: ranking formula on the rule set (Ranking method = Formula). Score can use journey attributes/tags, profile attributes (for example 
Gold loyalty), journey priority, or an AI model. Formulas need the Decisioning add-on and are currently Limited Availability. Assigned on the 
rule set, not per journey.

Event trigger types 
Unitary event — tied to one person. Purchase, cart abandon, login, form submit, loyalty milestone. That profile enters immediately. You can listen for 
several unitary events in the same journey (start and later steps). 
Business event — not tied to a person. Product back in stock, price drop, flight cancel, weather alert. It must be the first step. AJO then adds Read 
audience and enrolls everyone in that audience. Only one business event per journey. Expect 15 minutes to ~1 hour for audience export. 
Audience qualification — fires when a profile enters or exits an AEP audience (for example they hit Gold tier). No new event stream to implement; 
you use audience logic instead. Selected on the canvas, not in Events admin. Streaming qualification still has ~15–30 minutes Edge-to-Hub delay. 
For true real-time, use a unitary event.

How unitary events are identified 
Incoming data is XDM, usually via Streaming Ingestion / Web or Mobile SDK. 
●​ Rule-based: no special event ID. A condition on the payload (for example eventType = purchase and cart.value > 50) decides 
whether this journey listens. Capped around 5,000 qualified events/second per org. 
●​ System-generated: schema includes the Orchestration eventID field group. The payload must send the ID AJO generated. 
The payload must include a person identity (ECID, CRM ID, email, etc.) so AJO can stitch the event to a profile. Same event config can be reused by 
many journeys.
